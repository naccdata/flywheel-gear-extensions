# Changelog

## v0.0.4

- Adds a **required** `source_id` config field, placed in output filenames after the study id: `{study_id}-{source_id}-{module}[-{formver}]-{YYYY-MM-DD}[-{run_id}].csv` (e.g. `adrc-ingest-UDS-v4-2026-07-24-20260724T210431.csv`). **Breaking:** every output filename changes shape, and a job with an empty or omitted `source_id` fails at startup instead of falling back to the previous names
- `source_id` identifies the project a job read, which output filenames previously had no way to express. The gear's read source (`group_id`/`project_name`) and its write destination (the job's destination container) are independent, so one user-facing export can fan out across several source projects and write every job's output into a single destination project. In that arrangement the rest of the filename is identical by construction — same study, same date, same `run_id`, and the same module and form version wherever the source projects overlap — so two jobs produced byte-identical names in one project: Flywheel versioned the second write over the first, leaving one job's output reachable only as an older file version and silently absent from any listing without a version selector
- The value is caller-supplied rather than derived from `project_name`, keeping project-naming conventions outside the gear (as `run_id` keeps run semantics outside it). Deriving it would return a wrong-but-plausible answer for any project whose label does not match an expected prefix
- `source_id` is positioned before the module rather than after the date, because the trailing `run_id` is optional and two optional trailing segments cannot be parsed: given `...-2026-07-24-abc123.csv`, nothing distinguishes a run identifier from a source. A fixed position ahead of the date keeps one anchorable shape
- `source_id` is restricted to `[A-Za-z0-9]` and 16 characters, validated at startup for the same reason `run_id` is: filenames are `-`-delimited, so a `-`, `.`, or `_` inside a segment shifts every field after it. This rules out passing a raw project label such as `ingest-form-adrc`
- Retains `study_id` in the filename even where a per-study destination project makes it redundant within Flywheel: these CSVs are downloaded and spend the rest of their lives outside it, where the project name is gone and the filename is the only remaining label
- Consolidates the charset and length checks into one validator (`RUN_ID_PATTERN` becomes `FILENAME_SEGMENT_PATTERN`) and applies it to **every** config value that reaches a filename, not just `run_id` and `source_id`. `study_id` and each module name are now validated and stripped: both lead the filename, and a `-`, `.`, or `_` in either shifted every following segment and produced an unparseable name with no error. Existing `run_id` error messages are unchanged
- Fixes the form version segment, which could emit an arbitrary delimiter into the filename (`formver_label` in `common/`, shared with `gather_form_data`, promised a "filename-safe" label and enforced nothing — a `formver` of `3.0-draft` produced `v3.0-draft`, shifting every following segment). It now refuses any value carrying a `-`, `_`, `/`, or whitespace, labelling it `unknown` and logging it. A `.` remains allowed, since real form versions carry one — LBD `v3.1` — and the segment sits in a fixed, non-final position where a `.` cannot be read as a segment boundary
- The check is deliberately for filename safety, not for a well-formed version number: an odd-but-parseable value such as `3a` or `v3` still passes through as `v3a` / `vv3`, exactly as before. Rejecting those as well would change labels `gather_form_data` already emits and merge their rows into the `unknown` bucket — a change in that released gear's file count and column sets, for no parsing benefit. Every value that produces a usable filename today produces the same one after this change
- Consumers must therefore accept `v` followed by any letters, digits, and dots (or `unknown`) in the form version segment, not digits alone
- The formver property test now drives raw form-version values through `formver_label` rather than asserting that an alphanumeric string matches an alphanumeric pattern — the previous version could not have caught the above
- Documents the charset of every filename segment, and that config validation happens at job runtime, not at job creation: a caller sending a malformed value sees a failed job rather than a rejected request
- Documents that output is written to the job's destination container, which is independent of the project named by `group_id`/`project_name` — those name the project the gear reads
- **Refuses any job whose destination container is in a different group than the project it reads.** The gear reads whatever its config names using GearBot's key, which can read every center, and nothing in the job constrains that to the caller's own center — so without this, anyone able to launch the gear could point it at another center's `ingest-form` project and have that center's records written as CSVs somewhere they can download from. Defense in depth, not a replacement for Flywheel permissions: it closes the cross-center path for every trigger mechanism, however job-launch rights end up being granted
- The guard runs before the source group or project is resolved and before any data is gathered, so a refused run reads nothing, writes nothing, and reveals nothing about the project it was aimed at. It fails closed — a destination that cannot be identified or resolved, or that reports no group, is refused rather than allowed through unchecked
- Only the group is compared. Study-level scoping (an `adrc` export landing in `distribution-form-dvcid`) is left to the caller, since only the caller knows which study a run belongs to

## v0.0.3

- Fixes severe slowness on large centers (e.g. 1h52m for Arizona's ~25k-file retrospective project): replaced per-subject `get_files` queries with queries batched across subject ids (100 per batch, via Flywheel's OR-list filter syntax)
  - An earlier version of this fix issued a single unscoped query per module for the whole project; that was found in local testing to reliably time out on Flywheel's backend for large centers (retried for ~10 minutes then hard-failed with zero output) and was replaced with batching before release
- Adds progress logging (per-module start, and once per subject batch processed) to distinguish a slow-but-running job from a stalled one
- Reloads each batch's files concurrently (10 workers by default, `reload_workers` param) instead of one at a time, since a dataview-based bulk-fetch was found not to be viable (Flywheel's dataview columns only support fixed scalar fields, not the dynamic per-module field sets this gear needs) and per-file `.reload()` calls were confirmed by benchmark to be the dominant remaining cost for modules with many visits per subject (e.g. UDS): ~6.7x faster reload throughput in testing
- `batch_size` and `reload_workers` are both explicit, overridable parameters on `ModuleDataGatherer.gather_project_data`, and further exposed as gear config fields (`batch_size`, `reload_workers` in `manifest.json`), rather than a hardcoded constant
- `batch_size=100` validated via a sweep (25/100/200) against a small center and a large one (`retrospective-form`, ~25k files): 25 was slower everywhere; 200 was faster on the small center but a wash on the large one (reload volume dominates there, not query count) and did not reproduce the earlier timeout — confirms 100 has real margin rather than sitting at a fragile edge; kept as the default
- Writes each module's output file(s) immediately after that module finishes gathering, instead of waiting until every module has gathered — a later module's unrecoverable failure no longer discards an earlier module's already-completed output
- Adds an optional `run_id` config field, appended to output filenames after the run date (`{study_id}-{module}-{formver}-{YYYY-MM-DD}-{run_id}.csv`). Without it, filenames have day granularity, so a same-day re-export writes identical names and Flywheel replaces the files in place; the prior version is retained but unreachable through interfaces with no version selector, and nothing in the filename tells two runs apart. A caller-supplied identifier also groups files written by *separate jobs* of one user-facing export (e.g. one action fanned out across a center's `ingest-form-*` and `retrospective-form-*` projects), which no gear-generated value can do
- `run_id` is restricted to `[A-Za-z0-9]` and 32 characters, validated at startup: filenames are `-`-delimited and parsed by anchored patterns, so a value containing `-`, `.`, or `_` would make the trailing segments ambiguous. A malformed value fails the job with a clear message rather than silently emitting a filename consumers cannot attribute
- The run date and `run_id` are both read once per gear run rather than once per output file. Because output is now written as each module finishes gathering (above) — minutes apart on a large export — a value taken from the clock at write time would differ between modules: a run crossing midnight would stamp its modules with two different dates and appear to be two separate runs
- Omitting `run_id` reproduces the previous filenames exactly, with no trailing separator, so existing callers and parsers are unaffected
- Tags each output file with the gear name (`center-form-export`) so consumers can recognize export artifacts from typed file tags instead of matching filenames. Uses `update_file_metadata` with an explicit `container_type` — the input-tagging path used elsewhere in this repo resolves an existing container, which an output file does not have at gear runtime. Tagging failures are logged, not raised, so they cannot discard an export's already-written data. Note that the gear context only writes `.metadata.json` on a clean exit, so tags do not mark the partial output of a failed run
- Reuses one thread pool across all of a module's batches instead of constructing/tearing one down per batch
- Validated end-to-end against Arizona's `retrospective-form` project (3,003 subjects, ~13,980 sessions, a large legacy-import center — not confirmed to be the largest overall): 16m10s vs. the original ~1h52m per-subject baseline (~6.9x faster), byte-comparable output
- Known, accepted (not fixed) risk: concurrent `.reload()` calls share one Flywheel client/HTTP session across worker threads without an SDK-documented guarantee this is safe; observed correct in all testing to date

## v0.0.1

Initial release.

- Export form data for all subjects in a Flywheel group/project without a participant list
- Config-driven: `group_id`, `project_name`, `modules`, `study_id`
- Optional `formver_split` mode producing one CSV per (module, form version) pair
- Optional `include_derived` to include derived variables
- Resilient processing: logs warnings for individual subject failures, continues with remaining subjects
